# org-judgement-corpus: Telemetry and Pulse Archive for a Swift Portfolio

> A data repository that stores quality-gate telemetry, daily snapshots, and Pulse reports generated by org-judgement-system across a portfolio of Swift projects.

## Motivation

I needed a place for the Institutional Judgment System to write its output and for me to read it back over time. Each time org-judgement-system runs a quality gate on one of my Swift projects, it produces a structured set of records — metadata, complexity measurements, orientation checks, calibration results. Without a dedicated home, those records would either be scattered across individual project repositories or lost entirely. I wanted portfolio-wide quality to be trackable over time, which requires the data to accumulate in one place with a consistent layout.

The repository is not an application. Its two Swift targets are empty scaffolds that satisfy package conventions. The real content is the data it holds and the structure it imposes on that data.

## Approach

The layout is organized around two main trees. Under `telemetry/`, there are 111 project directories, each containing timestamped gate runs in the form `YYYY-MM-DD/HHmmss_*.json`. Each run produces four files: metadata, complexity, orientation, and calibration. Under `pulse/`, generated reports accumulate — 138 daily directories and 11 weekly directories, each with a `PULSE_*.json` and a Markdown `NARRATIVE_*.md`. The front matter of each narrative records which model wrote it.

A `manifest.yml` file acts as the registry of projects under observation. It records per-project lifecycle state, `changedAt` timestamps, optional tier overrides, and group membership — for example, the BusinessMath and BioFeedbackKit project families are listed separately from standalone tools.

Concurrent writes from CI are handled with a `.gitattributes` rule that sets `telemetry/*/index.jsonl merge=union`, allowing multiple runs to append to a per-project index without producing merge conflicts.

Data that was produced but could not be merged into the main corpus is kept in `stranded-telemetry/` with checksums and a README explaining why each record did not make it in. This keeps the main corpus clean while preserving the records for review.

The CI workflow, as documented in HANDOFF.md, clones the corpus and uses `ijs-telemetry push` from org-judgement-system to write new records back. The corpus itself does not orchestrate any of this — it is the destination.

## Results

Between the first commit on 2026-04-28 and the latest on 2026-11-10, the repository accumulated 1,997 commits across three contributors. That rate reflects the CI-driven write pattern: each gate run produces a commit, so the commit count is roughly proportional to the number of gate runs across all monitored projects. The corpus now holds telemetry for 111 projects, 138 days of Pulse reports, and 11 weekly Pulse summaries.

## Decisions

**Separating the corpus from the tooling.** org-judgement-system writes here but lives in its own repository. Keeping them separate means the corpus can be cloned by CI without pulling in the tool's dependencies, and the tool can be updated without touching the data layout.

**Union merge for index files.** The `.gitattributes` rule is the only concurrency mechanism. If two CI runs finish close together and both try to push, Git resolves the index append rather than producing a conflict. This is a narrow solution — it works for append-only JSONL indexes but would not generalize to other file types.

**Stranded telemetry as a first-class directory.** Rather than discarding gate output that failed checksum or arrived out of order, I keep it in `stranded-telemetry/` with a documented reason for exclusion. The records are there if I need to investigate a gap in the main corpus.

**No application code.** The Swift package scaffolding exists because the broader org-judgement-system ecosystem expects Swift packages. Having it here satisfies that expectation without adding any behavior that would need to be maintained.

**What is unfinished.** The `manifest.yml` schema and the pulse generation logic both live outside this repository, in org-judgement-system. If that tooling changes its output format, the corpus will silently accumulate differently-shaped records. There is no validation step in the corpus itself to detect drift. That is an open gap I have not addressed.
